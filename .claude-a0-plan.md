## publish-report root cause (found and fixed, commit a421b5e)
NOT a missing secret/permission. Job already had contents:write + secrets.GITHUB_TOKEN.
Real cause: outer `actions/checkout@v6` had `persist-credentials: true`, leaving a git
extraheader credential in place. The `grafana/plugin-actions/playwright-gh-pages/deploy-report-pages`
composite action then injects its OWN Authorization header via its `github-token` input during its
internal checkout of gh-pages -> two Authorization headers -> GitHub API 400
(`remote: Duplicate header: "Authorization"`). Fix: set `persist-credentials: false` on the outer
checkout so only the composite action's own auth applies. Pushed as commit a421b5e on upstream-clean-base.
Still need to confirm: (a) run for a421b5e goes green on publish-report, (b) peaceiris/actions-gh-pages
(used internally) successfully creates the gh-pages branch on first run since it doesn't exist yet on

## Follow-up: Playwright/Chromium + Grafana docker image caching (started, same branch)
User asked to add this now. Implemented directly in .github/workflows/ci.yml (not yet committed as of
writing this section -- see Housekeeping below for commit status):
- `playwright-tests` job (per e2e matrix version):
  - "Cache Playwright browsers": actions/cache@v4 on `~/.cache/ms-playwright`, keyed by
    `${{ runner.os }}-playwright-${{ hashFiles('yarn.lock') }}` (bumps automatically on yarn.lock changes,
    which is what pins the playwright version). Placed right before "Install Playwright Browsers".
  - "Cache Grafana base image" / "Load cached Grafana base image" / "Export Grafana base image for cache":
    actions/cache@v4 on a saved `docker save` tarball at /tmp/docker-cache/grafana-image.tar, keyed by
    `grafana-base-image-<NAME>-<VERSION>`. Skipped entirely for the `nightly` matrix entry (moving tag --
    caching it would pin a stale nightly build indefinitely). On cache hit, `docker load`s the tar before
    "Start Grafana" instead of re-pulling; on miss, `docker save`s the base image (`grafana/<NAME>:<VERSION>`,
    the Dockerfile's FROM target) right after Grafana successfully starts, so actions/cache's post-job step
    persists it for next time.
- `pr-screenshot-diff` job (single pinned version, GRAFANA_VERSION=12.4.0): same two cache patterns added
  (Playwright browsers cache before "Install Playwright Browsers"; Grafana base image cache/load before
  "Resolve merge base", export right after "Wait for grafana server (before)" -- the "before" and "after"
  builds within this one job already share Docker's local image cache once loaded/pulled once, so caching
  is only needed for the first pull/build of the job).
- Rationale: these were the two heaviest, most repetitive steps across every job/matrix entry (installing
  Chromium+deps fresh every run, and pulling/building large Grafana docker images fresh every run) that
  don't otherwise benefit from yarn's own dependency cache (`cache: yarn` on actions/setup-node only
  covers node_modules, not the separately-downloaded Playwright browser binaries or docker images).

### REGRESSION found in commit b26141a (this caching commit) — run 32575578468, FAILED (6 jobs)

### B0 CI debugging: two distinct bugs found and fixed
Initial B0 push (87f1a0d) had 7/13 e2e tests failing (panels 5,7,8,9,11,12,13). Local repro blocked by
sandbox network policy, so diagnosed entirely via CI job log analysis (temporary debug instrumentation
in tests/matrix-panel.spec.ts: pageerror/console-error listeners, later a DOM-dump afterEach hook --
both since removed).

**Bug 1 (panel 5): `src/matrix.js` line 593 -- FIXED in commit 5f33145.**
The categorical-legend branch of the legend-rendering code did `svg.append('g').selectAll('legendLabels')`
but `svg` was never defined in that scope -- the correct variable, already used by the sibling `range`-type
legend branch, is `svgLegend` (declared line 572: `const svgLegend = d3.select(\`#${legendClass}\`);`).
This threw `ReferenceError: svg is not defined` on EVERY page load (confirmed via 27 occurrences in one
job's log, across passing and failing tests alike, since panel 5's categorical legend is on the shared
13-panel dashboard loaded by every test). Fix: `svg` -> `svgLegend` on that line. Confirmed via next CI
run: 0 occurrences of `ReferenceError` in the log, and pass count went from 6->8 (panel 5 now passes).

**Bug 2 (panels 7,8,9,11,12,13): NOT a code bug -- test-infrastructure gap. FIXED in commit b56a041.**
Root cause: default Chromium viewport (1280x720, no override in playwright.config.ts) doesn't fit the
now-4-row-tall B0 dashboard (gridPos rows at y=0,15,30,45). Grafana lazy-mounts/virtualizes panels
outside the current viewport -- they don't exist as `[data-viz-panel-key]` elements in the DOM at all
until scrolled into view. Confirmed via a DOM-dump `afterEach` hook that queried every
`[data-viz-panel-key]` element on any non-passing test and logged its innerHTML: across the ENTIRE job
log (14 dump groups), the ONLY panel keys that ever appeared were panel-1,2,3,4,5,6,10 -- panels
7,8,9,11,12,13 never appeared even once, proving they were never mounted (not: mounted-but-broken).
This also explains why the first round of instrumentation (pageerror/console-error listeners) captured
nothing for these 6 panels -- there was no exception or error to capture, since Grafana simply never
rendered them into the DOM.
Fix: added `await panel.locator.scrollIntoViewIfNeeded();` immediately after `getPanelById(...)` and
before any assertion, in all 13 tests -- brings the target panel into the viewport so Grafana mounts it
before the visibility/svg checks run. Also removed both rounds of debug instrumentation now that root
causes are confirmed (they were explicitly temporary).
**UPDATE: the scrollIntoViewIfNeeded() fix in b56a041 did NOT work.** CI for that commit came back
8 passed / 6 failed -- same exact 6 panels (7,8,9,11,12,13) still failing, but now with a different
error: `locator.scrollIntoViewIfNeeded: Test timeout of 30000ms exceeded ... waiting for locator
('[data-viz-panel-key="panel-N"]')`. Root issue: Playwright locator actions (including
scrollIntoViewIfNeeded) auto-wait for the target element to attach to the DOM first -- but Grafana
never attaches these panels until they're already within the viewport. That's a chicken-and-egg
deadlock: you can't scroll an element into view if the act of finding it to scroll requires it to
already be attached, and it only attaches once already in view. So scrolling the specific target
locator can never work here.

**Actual fix (commit 4d92bd9): use a tall Playwright viewport so nothing needs scrolling.**
Added `viewport: { width: 1280, height: 2400 }` to `use` in `playwright.config.ts`. The dashboard's
panels span grid rows y=0 to y=60 (see `gridPos` in dashboard.json); 2400px comfortably fits the
whole thing plus Grafana chrome (nav/header/time-picker), so every panel mounts immediately on page
load with no scrolling needed at all. Left the (now redundant but harmless no-op)
`scrollIntoViewIfNeeded()` calls from b56a041 in place in the test file to minimize diff churn --
they resolve instantly since every panel is already in view.

**STATUS as of commit 4d92bd9: viewport fix was only PARTIAL. Superseded below.**
CI for 4d92bd9 came back version-dependent: the 6-way Grafana-version matrix job had 3/6 versions
green (13.1.4, 13.2.0, nightly -- all 13/13 passed) and 3/6 red (12.3.11, 12.4.9, 13.0.7 -- each
failing the SAME 6 panels every time: 7,8,9,11,12,13, via `scrollIntoViewIfNeeded` 30s timeouts,
i.e. never mounted). Initial read: "version-specific behavioral difference in older Grafana."

**That reading was WRONG -- overturned by the separate "Before/after panel screenshots" job.**
That job pins a single Grafana version (12.4.0) in its own container/run, so if the bug were purely
version-tied it should show the same ~6-panel failure signature. Instead it failed 11 of 13 panels
(only panels 1 and 2 passed) -- a much larger and DIFFERENT failing set than the matrix job's 12.x
runs (it additionally failed panels 3,4,5,6,10, which pass in the matrix job). A fixed per-version
code bug can't explain the failing set changing size and membership across different runs of
similar/same Grafana versions. Panels 1-2 passing everywhere (they're dispatched/mounted first,
before concurrent load ramps up) was the other key clue.

**Actual root cause: resource contention, not a code/version bug.**
`playwright.config.ts` had `fullyParallel: true` with no `workers` cap, so ~13 test browser
contexts hit ONE shared Grafana docker container concurrently. Older/slower Grafana versions
(12.x, 13.0.x line) fall behind under that concurrent load and miss panels' 30s mount timeout
(even across 2 retries); newer versions (13.1+/nightly) are fast enough to absorb it. The
before/after job's worse failure rate is consistent with a different/heavier concurrent-load
profile in that job's own process, not a different bug. Ruled out alternative theories before
landing here: reviewed `src/dataParser.ts` (colGrouping/rowGrouping resolution, sortType switch)
and `src/matrix.js` (category header height/width/gap calcs) for an asymmetric-grouping bug --
none found, all grouping paths are symmetric and null-safe. Also ruled out a pure
scroll-position/virtualization-by-row theory via gridPos dump: panel 10 sits in the same grid row
(y=30) as failing panels 7,8,9 yet passes in the matrix job, which a row-based theory can't explain.

**ACTUAL ROOT CAUSE FOUND: dashboard-level `preload: false`.**
`provisioning/dashboards/dashboard.json` had a top-level `"preload": false` (Grafana's default).
Per Grafana's own docs (lazy-loading-dashboards blog, dashboard JSON model docs): when `preload` is
false, panels only start their queries/mount once scrolled into view via Grafana's Scenes-based
intersection-observer lazy-load mechanism -- independent of the page's actual scroll geometry (a tall
viewport that puts everything "in view" on paper does NOT guarantee Grafana's own internal
intersection logic considers them visible early enough, especially before layout has fully settled).
This mechanism's behavior/timing clearly differs across the 13.0.7 -> 13.1.4 boundary, exactly
matching the pass/fail split (12.3.11/12.4.9/13.0.7 fail, 13.1.4/13.2.0/nightly pass). It also
explains why neither prior fix worked: viewport size doesn't affect Grafana's own intersection
threshold, and concurrency/serialization doesn't touch it either -- this is a lazy-load activation
gap in older Grafana versions, not a race or resource-starvation bug.
**Fix (this segment):** set `"preload": true` on the dashboard (dashboard.json), which makes every
panel start loading immediately regardless of scroll position, sidestepping the buggy lazy-load path
entirely. Also reverted the now-disproven `workers: process.env.CI ? 1 : undefined` in
playwright.config.ts (it cost ~5x wall-clock time -- jobs went from <2min to 9.5-9.7min -- with zero
verified benefit) and updated the viewport comment to stop citing the debunked theories. Kept the
tall 1280x2400 viewport since it's harmless and still avoids scrolling for screenshots.
