## publish-report root cause (found and fixed, commit a421b5e)
NOT a missing secret/permission. Job already had contents:write + secrets.GITHUB_TOKEN.
Real cause: outer `actions/checkout@v6` had `persist-credentials: true`, leaving a git
extraheader credential in place. The `grafana/plugin-actions/playwright-gh-pages/deploy-report-pages`
composite action then injects its OWN Authorization header via its `github-token` input during its
internal checkout of gh-pages -> two Authorization headers -> GitHub API 400
(`remote: Duplicate header: "Authorization"`). Fix: set `persist-credentials: false` on the outer
checkout so only the composite action's own auth applies. Pushed as commit a421b5e on upstream-clean-base.
Still need to confirm: (a) run for a421b5e goes green on publish-report, (b) peaceiris/actions-gh-pages
(used internally) successfully creates the gh-pages branch on first run since it doesn't exist yet on
the fork — should auto-create via orphan branch push, but verify in the logs once it runs.

## GitHub Pages settings answer (user asked, answered)
User asked whether to enable Pages via "GitHub Actions" source or point it at gh-pages branch.
Answer: use "Deploy from a branch" -> gh-pages (NOT the "GitHub Actions" build-and-deploy source).
Reason: deploy-report-pages uses peaceiris/actions-gh-pages internally, which pushes static report
HTML directly to a gh-pages branch -- it does NOT use the actions/deploy-pages + upload-pages-artifact
OIDC flow that the "GitHub Actions" Pages source expects. So Settings -> Pages -> Source must be
"Deploy from a branch", branch gh-pages, folder /(root). gh-pages branch must exist first (created by
this job's push) before that dropdown option will even find it.

## Follow-up: Playwright/Chromium + Grafana docker image caching (started, same branch)
User asked to add this now. Implemented directly in .github/workflows/ci.yml (not yet committed as of
writing this section -- see Housekeeping below for commit status):
- `playwright-tests` job (per e2e matrix version):
  - "Cache Playwright browsers": actions/cache@v4 on `~/.cache/ms-playwright`, keyed by
    `${{ runner.os }}-playwright-${{ hashFiles('yarn.lock') }}` (bumps automatically on yarn.lock changes,
    which is what pins the playwright version). Placed right before "Install Playwright Browsers".
  - "Cache Grafana base image" / "Load cached Grafana base image" / "Export Grafana base image for cache":
    actions/cache@v4 on a saved `docker save` tarball at /tmp/docker-cache/grafana-image.tar, keyed by
    `grafana-base-image-<NAME>-<VERSION>`. Skipped entirely for the `nightly` matrix entry (moving tag --
    caching it would pin a stale nightly build indefinitely). On cache hit, `docker load`s the tar before
    "Start Grafana" instead of re-pulling; on miss, `docker save`s the base image (`grafana/<NAME>:<VERSION>`,
    the Dockerfile's FROM target) right after Grafana successfully starts, so actions/cache's post-job step
    persists it for next time.
- `pr-screenshot-diff` job (single pinned version, GRAFANA_VERSION=12.4.0): same two cache patterns added
  (Playwright browsers cache before "Install Playwright Browsers"; Grafana base image cache/load before
  "Resolve merge base", export right after "Wait for grafana server (before)" -- the "before" and "after"
  builds within this one job already share Docker's local image cache once loaded/pulled once, so caching
  is only needed for the first pull/build of the job).
- Rationale: these were the two heaviest, most repetitive steps across every job/matrix entry (installing
  Chromium+deps fresh every run, and pulling/building large Grafana docker images fresh every run) that
  don't otherwise benefit from yarn's own dependency cache (`cache: yarn` on actions/setup-node only
  covers node_modules, not the separately-downloaded Playwright browser binaries or docker images).

  commit will be cold-cache by definition; need a *second* run to confirm actual cache hits/runtime win.

### REGRESSION found in commit b26141a (this caching commit) — run 32575578468, FAILED (6 jobs)
Root cause (single cause, explained both failure symptoms):
- `docker compose` has no top-level `image:` for the `grafana` service (it's build-only, base image only
  referenced inside the Dockerfile's `FROM grafana/${grafana_image}:${grafana_version}`). So
  `docker compose pull` is a no-op for it, and buildkit does NOT leave that FROM base image tagged in the
  classic `docker images` store after `docker compose up -d --build` -- confirmed via job log
  ("naming to docker.io/library/esnet-matrix-panel-grafana" -- only the FINAL built image gets a local tag).
  So `docker save grafana/<image>:<version>` failed with `Error response from daemon: reference does not
  exist` in BOTH jobs that do it (pr-screenshot-diff, and every playwright-tests matrix entry).
- That `docker save` step had no `if: always()`/`continue-on-error`, so its failure ABORTED the job before
  "Run Playwright tests" ever ran (test-outcome ended up literally "skipped"), which is why the
  *pre-existing* "Upload e2e test summary" step then failed too, with `PARENT_DIR` empty (its value comes
  from a `mv`-based composite-action step keyed off the (never-created) playwright-report dir, which never
  ran) -- this was NOT a separate regression, just a downstream symptom of the same docker save failure.
- **Fix (commit d207806, pushed)**: added an explicit `docker pull grafana/<image>:<version>` step (guarded
  by `cache-hit != 'true'`) right before the existing "Export Grafana base image for cache" step in BOTH
  jobs, so the tag actually exists locally before `docker save` runs. Moved pr-screenshot-diff's
  pull+export earlier (right after "Load cached Grafana base image", before the first `docker compose up`)
  since GRAFANA_IMAGE/VERSION are fixed env vars there, not matrix-dependent, so there's no need to wait for
  "Wait for grafana server (before)". Also made the export step `continue-on-error: true` in both jobs --
  caching is an optimization only, it must never be able to fail the actual e2e run again.
- [PUSHED as d207806] Also (user's follow-up ask, same commit): added a "Link report in job summary" step
  at the end of `publish-report`, echoing the gh-pages report index URL and this run's specific report URL
  into the GitHub Actions job summary (`$GITHUB_STEP_SUMMARY`) -- computed from `$GITHUB_REPOSITORY_OWNER`/
  `$GITHUB_REPOSITORY` env vars, no PR comment posted (no upstream-visible noise).
